## 三、★ 网络串线：`.1` 网关到底是什么（确认你的判断）

**结论：`172.29.0.1` / `172.30.0.1` / `172.31.0.1` 就是 Docker 宿主机本身，报告扫到的 `:8080 / :5000 / :9000` 是宿主机上你**其他**的资产，被容器网络串进来了。**

**证据链：**

1. `172.xx.0.1` 是每个 bridge 网络的**网关地址**，即宿主机在该网络上的接口：
   - tier-2 `netB` subnet `172.29.0.0/24` → 宿主机 = `172.29.0.1`
   - tier-3 `netA` subnet `172.30.0.0/24` → 宿主机 = `172.30.0.1`
   - tier-3 `netB` subnet `172.31.0.0/24` → 宿主机 = `172.31.0.1`

2. **本靶场仓库全量 compose 只发布这些端口**（`grep` 实测）：
   `8082:80`(tier1) `8083:80`(tier2) `8084:80`(tier3) `8085:8080`(t4) `8086:80`(t5) `8087:8983`(t6) `8088:8161` + `61616:61616`(t7)
   → **完全不含 5000 / 9000 / 宿主 8080**。所以报告看到的那些端口**不是任何一道题**。

3. 报告实际观测：`172.29.0.1` = 22/80/443/**5000**/**9000**；`172.30.0.1` = **8080**/**9000**；`172.31.0.1` = nginx 404 + SSH
   → 这是**远程靶机宿主 10.8.0.6 自身**的监听端口（`.1` = 该宿主在 bridge 上的接口）。

4. **指纹实测确认（2026-09-10，直接对 10.8.0.6 取证）**：

   | 地址 | 实际身份 | 响应证据 |
   |---|---|---|
   | `http://10.8.0.6:8080/` | **Hello::CTF（GZ::CTF 平台）** | `<meta content="Powered By GZ::CTF" name="description">`、`<title>Hello::CTF</title>`、`/favicon.webp` |
   | `http://10.8.0.6:9000/` | **Hello-CTF 管理面板** | `<title>Hello-CTF 管理面板</title>`（中文 UI） |
   | `http://10.8.0.6:5000/` | **AWDP-helper** | `<title>AWDP-helper</title>` + `cc-titlebar` / `modeswitch`（Patch 模式） |

   三者**均不属于本靶场仓库**（仓库全量 compose 只发布 8082-8088 与 61616），确认是你部署在 10.8.0.6 上的**赛事平台侧资产**。

5. 报告里「`hacker1` 会话 + `/api/edit/games/28/challenges`」——`games`/`hacker1` 是 GZ::CTF 的账号与数据模型，与第 4 条互相印证。

> **串线机制一句话**：容器 → 宿主始终可达（`internal: true` 只挡外网与外部主机，不挡宿主）；宿主在这些桥上的接口就是 `172.xx.0.1`，于是在容器里扫 `.1` 就等于扫 10.8.0.6 的**全部已发布端口**。tier-2 的「封锁边界」白名单 `-d 172.29.0.0/24 -j ACCEPT` 又把 `.1` 一起放行了。

**为什么会串（机制）：**

- `internal: true` 只阻断**容器↔外网 / 外部主机→容器**，**不阻断容器→宿主机**。宿主机在 bridge 上有 `172.xx.0.1` 接口，容器天然可达。
- 更严重的是 tier-2：其「封锁边界」白名单里写着 `-A OUTPUT -d 172.29.0.0/24 -j ACCEPT`——**网关 `.1` 恰好在这个网段内**，等于把宿主机**完全放行**了。
- tier-3 的 `web-edge` 根本没装 iptables，出站无限制，宿主机同样可达。

**风险等级：高（竞赛诚信）**

选手在 tier-2/tier-3 容器内即可访问宿主机全部已发布端口，包含**竞赛平台本体**（GZ::CTF / Hello-CTF / AWDP-helper）与**宿主机 SSH**。报告已经实测发起了对 GZ::CTF admin 的 26 组口令爆破与玩家侧路由枚举——只是没打进去。若被选手打穿，可直接读题库/flag/改分。

### 4.3 P1-1 出网探测假阳性的真实根因（新发现）

报告只说「结论与证据自相矛盾」。实际根因在 `pivothub/service/probe.py`：

1. **HTTP 探针解析过松 → 假阳性**（`probe.py:_parse`）：
   仅当输出中命中 `HTTP\s+(\d{3})` 才严格判定；**否则只要输出里不含字符串 `err`/`error` 且非空，就判 OK**。
   靶机侧 curl 被 DROP 时会走 fallback `wget`，回显类似 `curl: (28) Connection timed out` / `wget: unable to resolve host address` —— **都不含 `err`** → 被解析为 **HTTP=OK**。
   这完美解释了 tier-2 现象：白名单明明 DROP 了任意 TCP 80，探针却报 `HTTP=ok`。
2. **结论生成把 HTTP/TCP 混同**（`conclude`）：
   `if ok.get("TCP") or ok.get("HTTP")` → 只要 HTTP 假阳性为真，就输出「**可反向 TCP / HTTP 出网**」并推荐 chisel 反向。
3. **探针对端不对题**（`DEFAULTS`）：
   固定探 `8.8.8.8` / `www.baidu.com`。而 tier-2/t6/t7 的真问题是「能不能回连到**攻击机**的哪个端口」，公网可达性与题目无关。

→ 这三条合起来，是报告里「自动档两次部署 wait_callback 失败」的**面板侧主因**（靶机出站确实被封，但面板给出的判定是错的）。

### 七.1 L1 修复方案（具体到命令）

**技术要点先说清**：容器 → 宿主机自身 IP（如 `172.30.0.1:8080`）的流量，其目的地址是本机地址，走的是 **`INPUT` 链**，**不是 `FORWARD`/`DOCKER-USER`**。所以常见的「往 DOCKER-USER 里 DROP」在这里**不生效**，必须落在 `INPUT`。

本靶场占用的容器网段（从 7 个 compose 实测汇总）：

```
172.25.0.0/24  172.26.0.0/24        # tier-1
172.28.0.0/24  172.29.0.0/24        # tier-2
172.30.0.0/24  172.31.0.0/24        # tier-3
172.32.0.0/24  172.33.0.0/24        # t4
172.34.0.0/24  172.35.0.0/24        # t5
172.36.0.0/24  172.37.0.0/24        # t6
172.38.0.0/24  172.39.0.0/24        # t7
10.66.0.0/24                        # tier-3 核心区
```

**方案（推荐）— 在 10.8.0.6 宿主上，按来源网段拒绝入站，只放行必要端口：**

```bash
# 1) 先看一眼现在有哪些容器在往宿主打（确认不会误伤你自己的平台）
iptables -L INPUT -n -v --line-numbers

# 2) 逐段 DROP（示例：tier-2 的 netB）
iptables -I INPUT -s 172.29.0.0/24 -j DROP

# 3) 如果平台自身需要从某容器网段访问宿主（例如 GZ::CTF 要回调），
#    改成"只放行必要端口"的白名单写法，例如：
# iptables -I INPUT -s 172.29.0.0/24 -p tcp --dport 80 -j ACCEPT
# iptables -I INPUT -s 172.29.0.0/24 -j DROP

# 4) 持久化（按发行版选一）
iptables-save > /etc/iptables/rules.v4        # Debian/Ubuntu (netfilter-persistent)
# 或 iptables-save > /etc/sysconfig/iptables   # RHEL 系
```

**配套（低成本，建议同时做）**：把 tier-2 的白名单从"整段放行"收紧到具体应用，避免 `.1` 被顺带放行——

```diff
- -A OUTPUT -d 172.29.0.0/24 -j ACCEPT
+ -A OUTPUT -d 172.29.0.20 -j ACCEPT      # OA
+ -A OUTPUT -d 172.29.0.30 -j ACCEPT      # ops-docker(2375)
```

**验收（必做）**：从 `t2-web-edge` 容器内执行

```bash
nmap -Pn -p 22,80,443,5000,8080,9000 172.29.0.1     # 期望：全部 filtered/closed
nmap -Pn -p 2375 172.29.0.30                        # 期望：仍 open（那是考点）
```
